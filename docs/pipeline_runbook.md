# パイプライン運用ルールブック

## 全体フロー

役割定義は `agents/` 配下の6ファイル(analyst / marketer / architect / reviewer / promoter / director)。実行順序はこの通り。

```
アナリスト ── 前サイクルのデータを分析
    ↓
マーケター ── 次の記事テーマ・狙うASPを提案
    ↓
アーキテクト ── 記事の見出し構成・キーワード・リンク配置を設計
    ↓
レビュワー ── 設計図どおりに英語本文を執筆
    ↓
ディレクター ── Obsidian指示+チェックリストで最終確認(承認 or 差し戻し)
    │
    ├─ 差し戻し → アーキテクトまたはレビュワーに戻ってやり直し
    │
    └─ 承認 → プロモーター
                ↓
          Pinterest/SNS配信素材を作成
                ↓
          .envにAPI認証情報があれば実際に投稿(なければ画像生成のみで安全にスキップ)
                ↓
        (数日〜1週間データが溜まる)
                ↓
        次サイクルのアナリストへ
```

プロモーターは`scripts/run_promotion.py`を使って、Pinterestピンの画像生成→投稿、Xへの投稿までを実行できる(`agents/promoter.md`・`social_api_setup.md`参照)。認証情報が未設定の場合はエラーで止まらず、画像だけ生成して「投稿はスキップした」旨を報告する設計にしてある。

ディレクターを「レビュワー(執筆)の直後・プロモーター(配信)の直前」に置いているのがポイント。公開前の唯一のゲートなので、ここを飛ばすと質のばらつきがそのまま外に出てしまう。

## 各ロールの実体化の方法(現状の技術的制約)

このCowork環境には「常駐する6体のサブエージェント」を登録する仕組みは無い。実務上は、`agents/*.md` の「実行プロンプト」をそのままAgent toolの `prompt` に渡し、`description` にロール名を入れて1体ずつ呼び出す形で代替する。

```
例:
Agent({
  description: "マーケター: 次記事提案",
  prompt: "(marketer.md の実行プロンプト + アナリストの出力を貼り付けたもの)"
})
```

前の工程の出力(テキスト)を、次の工程のプロンプトにそのまま貼り付けて渡す「バケツリレー」方式。各ロールの出力は `docs/cycles/YYYY-MM-DD/` に保存しておくと、アナリストが後から振り返れる。

## Obsidian連携

Obsidianボルト「海外アフィ」に接続済み。共通ルールは `rule of foreign affiliate.md`(ボルト直下)にあり、`agents/director.md` から絶対パスで参照している。このプロジェクト自体もボルト内の `website/` フォルダに置いてあるため、毎週の自動実行でも既存記事・ルール・過去サイクルのログを実際に読み書きできる。

## 週次自動実行について

スケジュールタスク「affiliate-content-pipeline」により、毎週土曜9:08 JSTにこのパイプラインが自動起動する。この時刻は米国東海岸の金曜夜(Pinterest/Instagramのエンゲージメントが最も高い時間帯)に合わせてあり、ユーザーが日本時間の土曜朝に結果を確認してそのまま公開判断・投稿に移れるようにしている。

**2026-09-12更新: 試行回数を増やすため、1回の実行で記事3本を生成する構成に変更した。** アナリストは3本共通で1回だけ実行し、マーケター以降(アーキテクト→レビュワー→ディレクター→プロモーター)はテーマごとに独立して3周する。1本ずつ最後まで通してから次のテーマに進む(並行実行はしない)。3本のうちディレクター差し戻しが2回続いて承認に至らないテーマがあれば、そのテーマは見送り、無理に本数を揃えない。manifestは記事ごとに別ファイル(`cycle_manifest_YYYY-MM-DD_<スラッグ>.json`)として保存する(Xスレッドが記事をまたいで混線しないようにするため)。詳細は`.claude`のスケジュールタスク定義(`affiliate-content-pipeline`)を参照。

自動実行時、直近のPinterest/SNSデータが手元にない場合、アナリストは「データ不足のため一般的なベンチマークで代替」と明記した上で進める(`agents/analyst.md` 参照)。Pinterest/Xの投稿は`.env`(またはGitHub Secrets)にAPI認証情報が設定されていれば自動で行われ、未設定の間はピン画像の生成のみ行い、実際の投稿はスキップされる(`social_api_setup.md`参照)。3本体制により、SNS投稿数は記事1本あたり最大4件×3本=最大12件/週に増える見込み(Xは従量課金のため`.env`の`MAX_POSTS_PER_RUN`の見直しが必要になる場合がある)。

## Pinterest投稿の運用(2026-09-19更新)

### X投稿とピン投稿は別ワークフロー

| | 担当ワークフロー | 発火条件 | 内容 |
|---|---|---|---|
| X(ツイート) | `.github/workflows/run-promotion.yml` | `docs/cycles/cycle_manifest_*.json` のpush、および毎週土曜10:00 JST | `--skip-pins` 付きで実行。ツイートのみ |
| Pinterest(ピン) | `.github/workflows/pinterest-backlog.yml` | 毎日10:00 JST | 全マニフェストの未投稿ピンを1日4枚ずつドリップ投稿 |

**この分離は2026-09-19の事故を受けた対策。** マニフェストのpushで`run-promotion`が発火し、デザイン刷新前の古いピンが一度に大量投稿された。`run-promotion`側にピン投稿を戻すと、二重投稿になるうえ分散投稿の意味も失われる。戻さないこと。

ドリップにしている理由は、新規アカウントの大量一括投稿がスパム判定を受けるリスクを避けるため。`post_pin_backlog.py` はマニフェスト単位ではなく**ピン単位**で状態を持つ(`docs/cycles/.pins_posted.json`)ので、マニフェスト側の`.posted`マーカーとは独立して安全に再実行できる。

### ピン画像は投稿時に生成される

マニフェストは `title` / `subtitle` / `description` / `link` だけを持ち、**画像パスは持たない**。`post_pin_backlog.py` が投稿の直前に `generate_pin_image.py` を呼んで生成し、アップロード後に削除する。

このため、**過去に作られたマニフェストも投稿時点の最新デザインでレンダリングされる。** デザインを変更したときに古いマニフェストを作り直す必要はない。ピン画像ファイルをリポジトリにコミットする必要もない。

背景は `assets/pin-backgrounds/` からタイトル文字列をシードに決定的に選ばれる(同じ記事なら毎回同じ背景になる)。レイアウトは写真背景+上部テキストのオーバーレイ。上部オーバーレイを採用しているのは、下部配置より外部クリックが多かったとする事例調査に基づく(`generate_pin_image.py` の冒頭コメント参照)。

### 背景写真の補充プロセス

写真の採否は**人間が判断する**。パイプラインが自動で承認してはいけない。

1. `python3 scripts/fetch_pin_photo_candidates.py` — Pexelsから候補を取得し、`assets/pin-candidates/` に保存。同時に `photo_review.html` を生成
2. ブラウザで `assets/pin-candidates/photo_review.html` を開き、キーボード操作で承認/見送りを判定して書き出す
3. `python3 scripts/apply_photo_approvals.py` — `approved.json` を更新し、承認分を `assets/pin-backgrounds/` へ反映

2026-09-19時点の在庫: 候補96枚(12クエリ×8枚)、承認34枚、未レビュー62枚。プールが手薄になったら、まず未レビュー62枚を捌けば追加取得なしで増やせる。

## 差し戻しが多い場合の見直しポイント

- 同じ指摘が3サイクル続けて出る場合、その指摘はディレクターのチェックリストからアーキテクト/レビュワーの「実行ルール」自体に格上げして、そもそも発生しないようにする
- 例: 「健康効果を断定してしまう」指摘が続くなら、レビュワーの執筆ルールに具体的なNGワード集を追記する
