### 運用上の注記(今回新たに判明した点)
- `run_promotion.py`はピン画像を常に`_generated_pin_0.png`〜`_generated_pin_4.png`という固定ファイル名で manifest と同じディレクトリに保存する仕様だった。1回の実行で3記事分を処理する現行体制では、3本のmanifestを順にドライラン/本番実行すると、後続の記事の画像が前の記事の画像を上書きしてしまう(実際に3本目=ギフトガイド記事の画像だけが最後に残っていた)。今回は`generate_pin_image.py`を直接呼び出し、記事スラッグ入りのユニークなファイル名(`_generated_pin_<slug>_N.png`)で15枚すべてを再生成し直してからcommitした。GitHub Actions側は`run_new_promotions.py`がmanifestごとに処理しAPI投稿後に画像を破棄する設計のため実害はない見込みだが、ローカルでの記事本数拡大に伴う設計上の注意点として記録しておく。次回以降、この上書き問題を恒久的に解消するにはrun_promotion.py側でmanifestファイル名(スラッグ)を画像ファイル名に含める修正が望ましい。
- 作業用フォルダ(iCloud同期のObsidianボルト)上での`git`操作中、`.git/index.lock`を含むファイルのunlinkがサンドボックスのFUSEマウント越しに許可されず(`Operation not permitted`)、ローカルリポジトリが一時的にロックされる事象が今回も発生した(2026-09-12サイクルでも同様の事象を記録済み)。今回は`/tmp`配下にリポジトリを新規clone → そちらに変更ファイルをコピー → commit・pushする方式で回避した。作業フォルダ側の`.git`には触れていないため、既存の運用中リポジトリの状態には影響していない。

### git commit / push
`/tmp`にcloneしたリポジトリ経由で、記事3本・manifest3本・ピン画像15枚を`git add` → `git commit` → `git push`で`main`ブランチにプッシュ(コミットハッシュは下記コミット後に確定)。プッシュにより`.github/workflows/run-promotion.yml`がGitHub Actions上で起動し、Pinterest/X認証情報(GitHub Secrets)を使って実際の投稿処理が行われる設計。
